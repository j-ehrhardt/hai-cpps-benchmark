Command-Line Interface and Python Loader

HAI-CPPS v2 uses a validated command-line interface rather than the former mutable simulation API. Run all commands from the repository root.

Configuration File

code/benchmark_setup.json contains the ten benchmark topologies. Each top-level key names a dataset and contains:

  • ds_name: the dataset identifier, matching the top-level key;

  • model.modules: named module instances with a Modelica file, explicit module type, and enabled fault names;

  • model.edges: connections written as pairs of <module>.<port> endpoints; and

  • sim_setup: startTime, stopTime, numberOfIntervals, faultStart, and seed.

Use code/schemas/benchmark_setup.schema.json together with python code/sim.py validate --config <path> to validate a configuration. The semantic validator also checks module types, valid ports, fault names, mutually exclusive proxy pairs, timing, and referenced model files.

An abbreviated mixer configuration looks like this:

{
  "ds1": {
    "ds_name": "ds1",
    "model": {
      "modules": {
        "mixer0": {
          "files": "../models/Mixer.mo",
          "type": "mixer",
          "faults": {
            "anom_valve_in0": false,
            "anom_valve_in1": false,
            "anom_valve_in2": false,
            "anom_pump75": false,
            "anom_pump50": false,
            "anom_leaking": false
          }
        }
      },
      "edges": {
        "0": ["source0.port_out0", "mixer0.port_in0"]
      }
    },
    "sim_setup": {
      "startTime": 0,
      "stopTime": 10000,
      "numberOfIntervals": 10000,
      "faultStart": 2500,
      "seed": 20260831
    }
  }
}

Commands

Validate configuration only:

python code/sim.py validate --config code/benchmark_setup.json

Add --check-modelica --build-root work/model-check to compile-check every configured topology.

Run a campaign:

python code/sim.py run \
  --config code/benchmark_setup.json \
  --campaign {normal,single-fault,full} \
  --scenario ds1 \
  --output output/example \
  --build-root work/example \
  --seed 20260831

normal generates normal scenarios, single-fault requires compatible existing normal scenarios for comparison, and full generates normal scenarios followed by all enabled one-fault scenarios. The optional --module and --fault arguments select one normal/fault pair and require --scenario.

Python Loader

Use dataset_io.load_scenario_dataset for a leakage-safe release reader. It loads exactly one measurement view and never merges oracle values into that view.

from pathlib import Path

from dataset_io import load_scenario_dataset

scenario = load_scenario_dataset(
    Path("/path/to/scenario"), measurement_view="hybrid"
)
X = scenario.online_features

offline = load_scenario_dataset(
    Path("/path/to/scenario"),
    measurement_view="hybrid",
    include_oracle=True,
)
oracle_states = offline.oracle_states

online_features removes scenario_id, simulation_step, and simulation_time. Oracle states are available only with include_oracle=True and remain a separate table. Fault events, structural system knowledge, and technical timing are exposed as separate metadata mappings on the loaded scenario.
