Campaign Output and Data Directory

A v2.2 benchmark campaign writes a release of recordings, not one combined CSV. The default staging root is output/v2.2/ when you run python code/campaign.py --jobs 4 from the v2.2 repository root. This page describes the files created by that launcher. The separate code/simulate.py custom workflow writes a raw CSV instead; see Using the Simulation.

Campaign size and recording splits

The ten topologies, ds1 through ds10, contain 160 healthy recordings and 190 single-fault recordings in a complete campaign. Each topology has 10 healthy training, 3 validation, 2 calibration, and 1 test recording. Its enabled fault inventory determines how many fault recordings it has. Each fault proxy produces one persistent and one temporary test recording.

Directory layout

The campaign stores each topology as a shard. The topology name appears twice: first as the shard folder and then as the recordings folder. For example:

output/v2.2/
├── release_manifest.json                 # full validated campaign only
├── ds1_release_manifest.json             # one-dataset run only
├── ds1/
│   ├── README.md
│   ├── LICENSE
│   ├── campaign.json
│   ├── generation/                       # frozen code, models, config, dependencies
│   │   ├── README.md
│   │   ├── LICENSE
│   │   ├── requirements.txt
│   │   ├── requested_configuration.json
│   │   ├── code/campaign_configuration.json
│   │   ├── code/...
│   │   └── models/...
│   └── ds1/
│       ├── ds1_001_healthy/
│       ├── ...
│       ├── ds1_016_healthy/
│       ├── ds1_001_mixer0_anom_pump50_persistent/
│       ├── ds1_002_mixer0_anom_pump50_temporal/
│       └── ...
├── ds2/
└── ... ds10/

A full campaign writes release_manifest.json at the root after validation. A selected topology, for example --dataset ds1, writes ds1_release_manifest.json. Each summary records schema version, recording count, shard summaries, and the path to its validation report. The report and individual worker logs are under build/v2.2/campaign/logs/ by default, outside the release tree.

To check a finished full campaign again, run python code/campaign_check.py output/v2.2. The checker verifies expected counts and files, table alignment and time grids, artifact hashes, fault windows, and per-recording validation status.

campaign.json is the shard’s detailed manifest. It lists every scenario_id, split, seed, paired healthy recording, fault variant, start/end times, active duration, completion state, and coverage observations. Its status can be planned, running, failed, complete, or a coverage/signal review status. The generation/ snapshot freezes the generation code, Modelica models, requested configuration, replay configuration, requirements, and their SHA-256 digests.

The launcher uses output/v2.2/ as staging output. The source branch does not contain a generated data/ release. data/v2.2 is reserved for later promotion, and the campaign command refuses to write there directly. Do not mistake build/ logs or a custom run’s output/custom/ directory for benchmark recordings.

Scenario names and fault windows

A healthy name has the form ds1_016_healthy. A fault name has the form <topology>_<ordinal>_<module>_<fault>_<variant>, such as ds1_002_mixer0_anom_pump50_temporal. The fault ordinal 001 means persistent; 002 means temporary. The module and fault fields identify the single enabled intervention.

Each benchmark simulation has 25,000 one-second intervals from time 0 through 25,000. The canonical exported tables therefore have 25,001 rows, including both endpoints. The fault is configured to start at time 2,500:

  • Persistent: active from time 2,500 through the recording end; faultEnd is null and the active duration is 22,500 intervals.

  • Temporary: active on [2500, 7500); faultEnd is 7,500 and the active duration is 5,000 intervals.

The exact sampled value at an OpenModelica event boundary can be pre-event or post-event. Use technical_timing.json and the offline oracle flags when assessing boundary samples; do not infer physical onset from the first changed measurement alone.

The measurement, command, and oracle tables share scenario_id, simulation_step, and simulation_time identifiers. They are aligned row by row, but these three fields are excluded diagnostic features. The v2.2 release schema is 2.2.0.

Choose permitted diagnostic inputs

Read exactly one measurement view. The measurements list in permitted_inputs.json names allowed sensor columns; commands lists separately available controller outputs. actuator_responses is empty because independent speed, position, or power response sensors are not modeled. Oracle states, fault events, system knowledge, timing, and audit files remain separate offline information. This prevents a fault indicator or effective internal signal from leaking into an online diagnosis model.

import json
from pathlib import Path
import pandas as pd

recording = Path("output/v2.2/ds1/ds1/ds1_016_healthy")
policy = json.loads((recording / "permitted_inputs.json").read_text())
hybrid = pd.read_parquet(recording / "hybrid/measurements.parquet")
X = hybrid[policy["measurements"]]

# Use this only when controller commands are observable in your application.
commands = pd.read_parquet(recording / "commands.parquet")
X_with_commands = X.join(commands[policy["commands"]])

Use fault_events.json for labels after choosing inputs. The paired fault timing fields report threshold-qualified sampled differences, not an exact continuous-time causal onset. For reproducibility, retain each recording’s sim_setup.json and provenance.json with the tables you use.
